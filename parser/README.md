# Правовая памятка РО

Проект памятки по законодательству РО (`ro-memo.netlify.app`). Показывает
законы с форума `forum.russia.online` в структурированном виде: главы, статьи,
пункты, наказания. Работает как статичный сайт (Netlify), все данные хранятся
локально в браузере.

---

## 1. Как устроено

Пайплайн данных — от форума до сайта:

```
forum.russia.online  (Законодательная база)
        │
        │  run_raw.py  (Playwright + сохранённая сессия)
        ▼
   raw/<thread_id>.json   ← сырые посты с форума
   raw/<thread_id>.txt    ← то же, но читаемым текстом
        │
        │  parse.py  (разбор дерева, извлечение penalty)
        ▼
   data/<doc_id>.json     ← структурированное дерево документа
        │
        │  export_to_js.py  (оборачивает в window.XXX_DATA)
        ▼
   site/js/data/<doc_id>.js
   site/js/data/_manifest.js
        │
        │  браузер читает через Docs.get(docId)
        ▼
   app.html / law.html     ← страницы памятки
```

**Разделение ролей:**

- `raw/` — то, что пришло с форума, без изменений.
- `data/` — то, что распарсил скрипт (дерево с главами и статьями).
- `site/js/data/` — то, что читает фронт (те же данные, но в виде JS-модуля).
- `parser/` — все скрипты для преобразования данных.

Промежуточные форматы: `data/*.json` — источник истины. Если надо
посмотреть, что реально знает сайт — иди в `data/`. Если надо посмотреть,
откуда оно взялось — иди в `raw/`.

## 2. Быстрый старт

### Обновить один закон после правки на форуме

```bash
cd parser
python run_raw.py --only 4930     # 4930 — thread_id КоАП, см. config.json
python analyze.py                  # опционально: посмотреть, что изменилось
python parse.py --only ak
python check_penalties.py
python export_to_js.py
```

Открыть `site/law.html#ak-14.3` — проверить, что новая редакция отобразилась.

### Собрать всё с нуля

```bash
cd parser
python run_raw.py                  # займёт несколько минут
python parse.py
python check_penalties.py
python export_to_js.py
```

### Проверить, нет ли проблем в штрафах

```bash
cd parser
python check_penalties.py
```

Должно вывести `✅ Проблем не найдено.`

## 3. Скрипты

Все скрипты лежат в `parser/`, запускаются из этой же папки.

### `run_raw.py` — сбор данных с форума

**Что делает:** заходит на форум под сохранённой сессией (Playwright), проходит
по разделу «Законодательная база», собирает все посты каждой темы, сохраняет
в `raw/<thread_id>.json` и `raw/<thread_id>.txt`.

**Зависимости:** Python 3.8+, `playwright`, файл `storage_state.json` с
сохранённой сессией (cookies + localStorage).

**Запуск:**

```bash
python run_raw.py                  # все темы раздела
python run_raw.py --only 4930      # только КоАП по thread_id
python run_raw.py --no-ask         # без подтверждения
```

**Где взять `storage_state.json`:** логинишься на форум в обычном браузере,
потом через Playwright-скрипт один раз сохраняешь контекст. Файл уже лежит в
`parser/storage_state.json`. Когда сессия истечёт (форум её сбросит), надо
будет пересоздать.

**Что не делает:** не парсит структуру, не улучшает текст, не пишет в `data/`.
Только сырые посты.

**Маппинг thread_id → doc_id** берётся из `config.json` (`threads`).

### `analyze.py` — обзор структуры

**Что делает:** проходит по всем `raw/*.json`, считает, сколько в каждом
документе глав, статей, разделов, пунктов, есть ли преамбула, содержание.
Пишет отчёт `parser/analyze_report.json` и печатает сводную таблицу.

**Когда полезно:** когда добавляешь новый документ и не уверен, к какому типу
он относится (A/B/C/D). Сначала прогоняешь analyze, смотришь цифры, потом
решаешь.

**Запуск:**

```bash
python analyze.py
```

### `parse.py` — основной парсер

**Что делает:** читает `raw/*.json`, определяет тип документа (A/B/C/D),
строит дерево узлов (части → разделы → главы → статьи → пункты → подпункты),
извлекает `penalty` из строк «Наказание: …», сохраняет в `data/*.json`.

**Запуск:**

```bash
python parse.py                    # все документы
python parse.py --only ak          # только один
python parse.py --show ak          # напечатать дерево, не сохранять
```

**Что извлекает из текста:**

- `meta.marks` — из заголовков статей вида `Статья 14.3. (Ф/Р) Текст`.
- `meta.priorityStars` — из строк вида `Приоритет розыска - 4`.
- `penalty` — из строк вида `Наказание: …`.
- `preamble` и `signature` — для типа D.

**Что НЕ извлекает** (хотя в `shema.json` они есть): `conviction`,
`jurisdiction`, `resolution`, `group`, `related`. См. раздел 7.

**Зависимости:** `config.json` (для коротких имён документов `titles`).

### `check_penalties.py` — валидация штрафов

**Что делает:** проходит по всем `data/*.json`, ищет три класса проблем:

- инверсии `from > to` (регулярка перепутала границы),
- «от X до Y» в `penalty.raw`, но без `from`/`to` в `types` (регулярка не
  поймала),
- штраф упомянут, но `types` без чисел вообще.

**Запуск:**

```bash
python check_penalties.py
```

**Как реагировать:** если что-то нашлось — открыть `raw/<doc_id>.json`, найти
статью, посмотреть формулировку. Обычно это нестандартный формат («от 5 тыс.»,
«не менее 500», разрыв строки между числами). Скинь строку — доработаем
`RE_RANGE` в `parse.py`.

### `export_to_js.py` — конвертер для фронта

**Что делает:** читает `data/*.json`, пишет `site/js/data/<doc_id>.js` в формате
`window.XXX_DATA = {...};`. Плюс генерирует `site/js/data/_manifest.js` со
списком всех документов и их короткими названиями.

**Запуск:**

```bash
python export_to_js.py
```

**Что нужно помнить:** после каждого `parse.py` надо вызывать `export_to_js.py`,
иначе фронт не увидит изменений (он читает `.js`, а не `.json`).

Список документов для экспорта задан в `export_to_js.py` (константа `DOC_IDS`),
не в `config.json`.

## 4. Форматы файлов

Каноническая схема структуры описана в `shema.json` в корне проекта. Ниже —
краткий обзор, подробности там.

### `raw/<thread_id>.json` — сырые посты

```json
{
  "thread_id": "4930",
  "thread_url": "https://forum.russia.online/threads/...",
  "doc_id": "ak",
  "thread_title": "КОДЕКС РО ОБ АДМИНИСТРАТИВНЫХ ПРАВОНАРУШЕНИЯХ",
  "revision": "27.09.2026",
  "post_count": 1,
  "first_post_id": "post-16504",
  "posts": [
    {
      "post_id": "post-16504",
      "author": "Марк Брагин",
      "date": "25.08.2026",
      "last_edit": "27.09.2026",
      "text": "ПОЛНЫЙ ТЕКСТ ПОСТА…"
    }
  ]
}
```

Если закон разбит на несколько постов, они все лежат в `posts`, в порядке
появления на форуме. Парсер склеивает их тексты через `\n` в один документ.

`revision` берётся как `posts[0].last_edit` (если пост редактировали),
иначе — `posts[0].date`.

### `data/<doc_id>.json` — дерево документа

```json
{
  "id": "ak",
  "title": "КоАП РО",
  "full_title": "КОДЕКС РО ОБ АДМИНИСТРАТИВНЫХ ПРАВОНАРУШЕНИЯХ",
  "revision": "20.09.2026",
  "source_url": "https://forum.russia.online/threads/...",
  "post_id": "post-16504",
  "preamble": "",
  "signature": "Нормативно-правовой акт подписан ...",
  "type_detected": "A",
  "nodes": [ ... ]
}
```

**Типы узлов в `nodes`:**

| type           | Обязательные поля                     | Смысл                              |
|----------------|---------------------------------------|------------------------------------|
| `part`         | `title`, `children`                   | ОБЩАЯ / ОСОБЕННАЯ ЧАСТЬ            |
| `section`      | `number`, `title`, `children`         | Раздел                             |
| `chapter`      | `number`, `title`, `children`         | Глава                              |
| `article`      | `number`, `title`, `children`, `meta?`, `penalty?` | Статья                  |
| `paragraph`    | `number?`, `text`, `children?`        | Пункт внутри статьи                |
| `subparagraph` | `number`, `text`                      | Подпункт                           |
| `note`         | `text`                                | Примечание                         |

**`meta` у статьи** — сейчас заполняется только двумя полями:

- `marks: ["Ф", "Р", ...]` — метки фракций.
- `priorityStars: 1..5` — приоритет розыска.

**`penalty` у статьи** — появляется, только если в тексте была строка
«Наказание: …». Формат:

```json
"penalty": {
  "raw": "административный штраф от 10 000 до 30 000 рублей...",
  "types": [
    { "type": "штраф", "currency": "RUB", "from": 10000, "to": 30000 },
    { "type": "арест", "to": 10, "unit": "суток" },
    { "type": "конфискация" }
  ]
}
```

Возможные `type` в массиве `types`: `штраф`, `арест`, `лишение свободы`,
`лишение права`, `конфискация`, `обязательные работы`, `предупреждение`,
`приостановление деятельности`.

**Как парсятся штрафы.** Регулярка `RE_RANGE` ловит «от X до Y», допускает
«рублей» между числами («от 50 000 рублей до 100 000 рублей»). Если в статье
несколько диапазонов (например, для гражданина и для должностного лица), они
сжимаются в один широкий `min(from)…max(to)`. Точность по частям не
сохраняется — это компромисс, чтобы не править вручную.

### `site/js/data/<doc_id>.js` — обёртка для фронта

Один файл на документ:

```javascript
window.AK_DATA = {"id":"ak","title":"КоАП РО",...};
```

Плюс `_manifest.js`:

```javascript
window.DOC_MANIFEST = {"ak":{"title":"КоАП РО","revision":"20.09.2026",...},...};
```

Фронт читает эти глобальные переменные через `Docs.get(docId)` (см.
`site/js/data.js`).

## 5. Типы документов

Парсер автоматически определяет структуру по тексту. Типов четыре — A, B, C, D.
Результат записывается в `type_detected`.

### A — обычный закон

Признаки: главы «Глава 1.» или «Глава IV.», статьи «Статья 14.3.», пункты «1.»,
подпункты «а)», «1)». Самый частый тип.

**Примеры:** `ak`, `uk`, `pk`, `tk`, `fsb`, `police`, `gibdd`, `sk`,
`prosecutor`, `duma`, `government`, `ministries`, `courts`, `territories`,
`advocacy`, `business`, `service`, `secret`, `weapons`, `vs`, `fso`,
`immunity`, `emergency`, `parties`, `health`.

### B — ПДД

Особый формат: разделы «Раздел 1.», пункты «1.1.», «1.2.» играют роль статей,
подпункты «1)». Внутри каждого пункта — свой текст.

**Пример:** `pdd`.

### C — этика

Разделы «Раздел I.», статьи «Статья 1.», пункты «1.1.» и «а)». Глав нет, только
разделы.

**Пример:** `ethics`.

### D — Конституция

Есть преамбула, содержание (TOC) и главы «Глава I.». Парсер пропускает TOC,
читает пункты «1.», «2.» внутри статьи.

**Пример:** `constitution`.

**Как определить, какой тип присвоился** — по полю `type_detected` в
`data/<doc_id>.json` или в выводе `parse.py --only <doc_id>`.

**Если новый документ не подходит ни под один тип** — сначала прогони
`analyze.py`, посмотри цифры. Если структура уникальна, надо писать
новый `parse_type_X` в `parse.py`.

## 6. Workflow-сценарии

### Обновить существующий закон

1. Найти `thread_id` документа в `parser/config.json` (секция `threads`,
   обратный маппинг `doc_id → thread_id`). Например, `ak` → `4930`.
2. Собрать свежие посты с форума:
   ```bash
   python run_raw.py --only 4930
   ```
3. (Опционально) Посмотреть, что изменилось:
   ```bash
   python analyze.py
   ```
   Сравнить `chars` и `revision` с прошлым запуском.
4. Перепарсить в дерево:
   ```bash
   python parse.py --only ak
   ```
5. Проверить штрафы:
   ```bash
   python check_penalties.py
   ```
6. Обновить JS для фронта:
   ```bash
   python export_to_js.py
   ```
7. Открыть на сайте `law.html#ak` → проверить, что новая редакция и суммы на
   месте.

### Добавить новый закон

1. Открыть тему закона на форуме, скопировать `thread_id` из URL (число после
   `/threads/...`).
2. Добавить в `parser/config.json`:
   - в `threads`: `"<thread_id>": "<doc_id>"` (придумать короткий `doc_id`),
   - в `titles`: `"<doc_id>": "Короткое название"`.
3. Собрать посты:
   ```bash
   python run_raw.py --only <thread_id>
   ```
4. Определить тип документа:
   ```bash
   python analyze.py
   ```
   Посмотреть цифры по новому файлу. Если он явно не A/B/C/D — надо доработать
   парсер.
5. Распарсить:
   ```bash
   python parse.py --only <doc_id>
   ```
6. Проверить, что дерево адекватное:
   ```bash
   python parse.py --show <doc_id>
   ```
7. Прогнать `check_penalties.py`, исправить проблемы.
8. Добавить `doc_id` в `DOC_IDS` в `parser/export_to_js.py`.
9. Экспортировать:
   ```bash
   python export_to_js.py
   ```
10. Добавить `<script src="js/data/<doc_id>.js"></script>` в `app.html` и
    `law.html`, а также `doc_id` в соответствующие группы в `render.js`
    (константа `GROUPS`).
11. Проверить на сайте.

### Проверить, всё ли ок с данными

```bash
cd parser
python analyze.py              # общая картина: сколько чего в каждом документе
python check_penalties.py      # валидация штрафов
```

`analyze_report.json` после прогона `analyze.py` — удобный способ сравнить
текущее состояние с прошлым (например, если что-то резко упало в количестве
статей, значит парсер сломался на новом формате).

## 7. Известные ограничения и TODO

### Парсер не создаёт поля, которые есть в `shema.json`

Схема описывает более богатую структуру, чем та, что умеет делать `parse.py`.
Не реализовано:

- `meta.conviction` — судимость.
- `meta.jurisdiction` — кто рассматривает (ФСБ, МВД и т.п.).
- `meta.resolution` — что делать при задержании.
- `meta.group` — группировка статей по темам.
- `related` — связи со статьями из других кодексов.

Это надо либо дописывать в парсер (когда появится единый формат на форуме),
либо оставить как «ручные поля для отдельных статей», либо убрать из
`shema.json` как преждевременные.

### Дубли номеров статей

Если в документе есть две статьи с одинаковым номером (например, `Статья 1.` в
разных разделах), обе получат один `node_id` (`uk-1`), и `Docs.findArticle`
найдёт только первую. Обработка дублей (`node_id` с суффиксом `-1`) описана в
`shema.json`, но не реализована.

### Многочастные статьи со штрафами

Диапазоны для разных категорий (гражданин / должностное лицо / организация)
сжимаются в один широкий `min…max`. Точность по частям не сохраняется.

### Числа прописью и коэффициенты

- «не менее пяти тысяч рублей» — не парсится.
- «до ста тысяч» — не парсится.
- «штраф в размере 500 МРОТ» — не парсится.

Регулярка ловит только цифры. Если такие формулировки появляются часто — надо
расширять `parse.py`.

### Мёртвые поля в `config.json`

Поля `location`, `blacklist`, `schemas` нигде не используются. Оставлены как
резерв. Если уверен, что не понадобятся — можно удалить, чтобы не путали.

### `run_raw.py` требует актуального `storage_state.json`

Когда сессия на форуме истечёт, скрипт начнёт получать 403/логин-страницу
вместо данных. Надо пересоздать `storage_state.json`: залогиниться в браузере
и сохранить контекст. Инструкция — в комментариях в `run_raw.py` или в
документации Playwright.

## 8. Отладка

**«ПРОПУЩЕН ДИАПАЗОН» в `check_penalties.py`.**

Найти статью в `raw/<doc_id>.json`, посмотреть формулировку. Скорее всего,
нестандартный формат. Скинь строку — доработаем `RE_RANGE`.

**Парсер выдал странное дерево (`parse.py --show <doc>`).**

Сохрани вывод в файл, найди, где поехало. Обычно это либо нестандартный
заголовок главы/статьи, либо лишние пустые строки. Кусок `raw/` вокруг
проблемного места — скинь.

**В `data/<doc_id>.json` пустые главы/разделы.**

`cleanup_nodes` не убрал, потому что у них есть `children` (пустые
paragraph-ы). Проверь, нет ли в `raw/` одиноких заголовков глав без статей.

**На сайте не обновляются данные.**

Скорее всего, забыл `export_to_js.py`. Он обязателен после `parse.py`. Фронт
читает `site/js/data/*.js`, а не `data/*.json`.

**Кнопки ★/🗑 не переключаются после удаления через модалку.**

Это было исправлено в `modal.js` — добавлены вызовы
`Render.refreshRowButtons` и `Render.refreshArticleButtons`. Если снова
воспроизводится — проверь, что файлы именно последней версии.

**localStorage замусорен старыми ключами.**

Если в браузере остались ключи `ro-memo-favorites`, `ro-memo-cart`,
`ro-memo-favs`, `ak-favs` (с дефисами), их надо почистить: они от старой
версии проекта. Актуальные ключи — с подчёркиваниями: `ro_memo_favorites`,
`ro_memo_cart`, `ro_memo_profile`.

```
проект памятки v2/
├── raw/                      # сырые посты с форума
│   ├── 4930.json             # КоАП
│   ├── 4930.txt              # он же, читаемым текстом
│   ├── 4805.json             # УК
│   └── ...
│
├── data/                     # обработанные деревья документов
│   ├── ak.json
│   ├── uk.json
│   └── ...
│
```

## 10. Технологии

**Парсер:** Python 3.8+, Playwright (для `run_raw.py`). Стандартные библиотеки
(`json`, `re`, `pathlib`, `argparse`) — для всего остального.

**Фронт:** статичный HTML + CSS + JS, без сборщика. Все данные читаются из
глобальных `window.XXX_DATA`. Состояние пользователя (профиль, избранное,
корзина) хранится в `localStorage`.

**Хостинг:** Netlify (для `site/`).
